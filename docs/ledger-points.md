# 口座タブの「ポイント」区画（#1533）

家計簿の口座タブの、円の口座グループの後ろ（非表示の口座の前）に「ポイント」区画を出す。**円の合計には含めない。**

- **Zaimのポイント・マイル**: AIDEの `GET /api/money/summary` の `points`（`name`・`amount`・`unit`・`lastUpdatedAt`）を1件1カードで出す。
  読むのは管理者（`isZaimAllowedEmail`）だけ。`points` が無い古いキャッシュでは出ない（AIDE側は guchi-apps/aide#872）
- **単位**: AIDEの `unit`（`point`/`mile`）を優先し、無ければ名前の「マイル」「マイレージ」で決める（`lib/ledger-points.ts`）。
  Zaimはマイルにもptと¥相当を付けるが、円としては扱わない
- **古い表示**: `lastUpdatedAt` が3日より前なら `isExternalBalanceStale` で目立たせ、上の「古い口座があります」にも並べる。
  AIDEが結び付けられず `null` のときは「古い」は出ない
- **家計簿の口座（種類が「ポイント」）**: カフェテリアポイントなど。円の口座グループ・総合計から外し、この区画に
  いつもの口座カード（押すと取引履歴）で出す。並び替えの保存では非表示の口座と同じく末尾に保つ
- **AIDEの読み込み**: 口座タブの表示（`getExternalBalancesAction`）だけが `includePoints` を付けて読む。残高合わせは付けないので、
  ポイントのためにAIDEへの依存は増えない
- **PayPayポイントなどを手入力で管理する**: 種類「ポイント」の口座（例: 「PayPayポイント」）を作る。1pt＝1円として家計簿の仕組み
  （取引・支払いを分ける・残高調整）をそのまま使い、外部連携はしない。カードと口座の詳細画面の残高は円（`¥`）ではなく
  `pt` で出す（`formatLedgerPointBalance`）。口座の詳細画面の「残高を合わせる」から、アプリで見た残高を入れると差額を
  残高調整の取引として残す（`BalanceAdjustDialog` を共用。入力欄は「実際の残高（pt）」）。
  取引の一覧の金額は従来どおり `¥` 表記のまま

## 利用額からのポイントの自動計算（PayPayポイントなど）

種類「ポイント」の口座に、貯まる元の口座（PayPayなど）・計算を始める日・基本還元率・付与までの日数を持たせると、
元の口座の確定した支出から**毎回計算して**出す（取引は増やさない）。算出は `lib/point-accrual.ts`、DBからの読み込みは
`lib/ledger-point-service.ts`（`loadPointAccruals`）。

- **持ち方**: `LedgerAccount.pointSourceAccountId`・`pointStartDate`・`pointRateBp`（0.5% = 50）・`pointBaseLagDays`（既定1）・`pointBonusLagDays`（既定31）。
  `LedgerEntry.pointRateBp` は取引ごとの還元率の上書き（null は基本）。`pointSourceAccountId` は外部キーを張らず、口座の削除で外し、結合で付け替える
- **計算**: 取引ごとに金額 × 還元率を**切り捨て**（返金は絶対値を切り捨てて引く）。数えるのは開始日以降の確定した支出（支払いを分けた取引はその口座が払った分）。反映待ちは数えない
- **ボーナス**: 取引の還元率が基本を超えたとき、超えた分がボーナスで、支払い日から `pointBonusLagDays` 後に付与。基本分は `pointBaseLagDays` 後。上書きが基本以下なら、その率が基本分でボーナスは0
- **ラグ**: 付与日（当日を含む）を過ぎた分が「利用可能」、まだの分が「付与予定」（カードと詳細画面に「付与予定 N pt（最短 M/D）」）
- **残高**: 表示する残高 ＝ 家計簿の計算 ＋ 利用可能（`pointBalanceOf`）。付与予定は含めない。**「残高を合わせる」は目標から利用可能分を引いた差額を調整にする**（`setAccountBalance`。引かないとアプリの残高に合わせるたびに二重に数える）
- **PayPayの付与ルール**（2026-11-23 時点の公式ヘルプ c0089・c0413）: キャンペーン等の特典ポイントは原則「支払いの翌日から起算して30日後」に付与（= 支払い日から31日後）。
  **通常の基本還元の付与日、付与後すぐ使えるか、200円ごとの計算・端数処理は公式ヘルプに記載が無い**ので、基本分の日数は口座ごとに直せる設定にし、端数は取引ごとの切り捨てとした。アプリの「付与予定」と合わなければ日数を直す


## 取引の入力画面の「ポイント還元」欄（#1583）

支出の入力画面（`components/ledger/entry-form-dialog.tsx` → `point-earnings-section.tsx`）の口座の下に、いつも出す。
支払いごとに「どのポイント口座に何pt付いたか」を `LedgerPointEarning`（取引・口座ごとに1行）で持つ。取引は増やさない。

- **自動計算の口座（PayPayポイントなど）**: 払った口座（支払いを分けたときはその口座の分）が貯まる元なら、その口座の行を
  見込み（基本還元率で計算）つきで出す。ポイント数を入れると、その取引の自動計算を上書きする。**基本還元率で計算した分までが基本分、
  超えた分がボーナス**（`accrualFor`。還元率の上書きと同じ分け方なので、旧来の還元率をポイント数へ換算しても結果は変わらない）
- **還元率（`LedgerEntry.pointRateBp`）からの移行**: 入力欄は還元率からポイント数へ変えた。還元率を入れていた取引は、開くと
  ポイント数へ換算して見せ（`pointsFromRate`）、保存でポイント数の行に置き換えて `pointRateBp` を `null` に戻す（率とポイント数で
  二重に数えないため。`parseEntryInput` が `pointEarnings` を受け取ったら必ず外す）。保存し直していない取引は従来どおり率で数える
- **手入力のポイントカード（Vポイント・楽天ポイントなど）**: 「ポイントカードを追加」で、種類「ポイント」の口座を選んでポイント数を入れる。
  付与日の設定を持たないので**支払い日に付与済み**として残高に足す（`computeManualPointAccrual`）。初期残高の基準日より前・照合待ち（`MATCH_PENDING`）の
  取引は数えない。反映待ち（カード明細待ち）は数える（ポイントはお店で付いているため）
- **Zaimで自動反映されるものは対象外**: Zaimのポイント・マイル（AIDEの残高）は家計簿の口座ではないので候補に出ない。家計簿の口座でも、
  Zaimの口座と対応付けたもの（`LedgerSourceAccountMapping` の `provider = "zaim"`・`target = "ACCOUNT"`）は、Zaimの同期で残高が動くため
  候補に出さず、残高にも足さない（`canEarnPoints`。保存時もサーバーで確かめる）
- **一覧の印**: 取引ごとに、入れたポイント数と自動計算の見込みの合計を「+19pt」で出す（`entryPointTotal`）
- **後始末**: `relationMode = "prisma"` のため、取引を消す経路（削除・一括削除・ルール・対応表・CSVの取り消し・Zaim新着の確認・全消去）では
  立て替え・支払いと同じく明示的に消す。反映待ちとカード明細を1件にまとめるときは残る取引へ移し（`movePointEarnings`。同じ口座の行が
  両方にあれば残る側を残す）、ポイント口座の削除では行を消し、口座の結合では結合先へ付け替える（`reassignPointEarningAccount`）。
  Zaimの同期で消える取引にポイントが付いていれば、利用者の関連付けとして消さずに残す
