# 返金と支払い明細の紐づけ（#1259）

返金の取引（マイナスの支出、または収入）が、どの支払い（支出の取引）への返金かを `LedgerEntry.refundOfEntryId` に持つ。
**印を付けるだけで、金額・残高・按分などの集計は変えない**（`subscriptionId` と同じ考え方）。

- 返金元を付けられるのは `isRefundAmount`（マイナスの支出・プラスの収入）、返金元にできるのは `isRefundTarget`（プラスの支出）。`lib/ledger-refund.ts`
- 1つの返金に付けられる返金元は1件。1つの支払いに返金は何件でも付けられ、一覧の「返金あり」と編集ダイアログの「返金後の実質負担」に出る
- 外部キーは張らない（relationMode = prisma）。**読み出し（`loadRefundLinks`）は、指す先が無い・支出でない行を無視する**ので、
  取引を消す経路で解除し忘れても画面は壊れない（id は再利用されない）
- 解除・付け替えを入れた経路: `deleteEntryInTx`・`deleteEntriesInTx`（`clearRefundLinks`）、カード明細の照合（`moveRefundLinks`。
  確定側が消えて反映待ち側が残るため、返金の紐づけを残る側へ移す）、反映待ち支出のカード明細への添付（`attachToStatement`。
  逆に反映待ち側が消えてカード明細が残るので、同じく残る側へ移す。#1274）。ほかの削除（取り込み・ルール・全消去など）は読み出し側の無視に任せている
- 候補は `loadRefundCandidates`。同じ店 → 返金額以上 → 日付が近い順（`rankRefundCandidates`）

## まとめて払った分の受け取り（#1661）

自分がまとめて払い（カードなど）、みんなの分をあとで現金などで受け取るときも、返金と同じ紐づけで記録できる。
受け取ったお金を**マイナスの支出**（キーパッドの `±`）で入れ、元の支払いを「返金・受け取り元の支払い」で選ぶ。

- 返金元の候補（`loadRefundCandidates`）は、受け取りの日より後の支払いも **60日後まで** 出す（`refundCandidateDateMax`）。
  店名・品目名で探すときも同じ上限が付く（前の日付には上限なし）。先にお金を受け取り、あとからカードの請求が取り込まれるケースのため
- マイナスの支出で元の支払いを選ぶと、**カテゴリが空の品目だけ**に元の支払いの主なカテゴリ（カテゴリの付いた品目のうち金額が最大のもの。
  `mainCategoryOf`）を入れる。手で選んだカテゴリは変えない。収入の受け取りは支出のカテゴリを持てないので変えない
- 支払いの側からも紐づけられる（編集画面の「先に受け取った分を紐づける」。`RefundReceiptsPicker`）。候補はどこにも紐づいていない
  マイナスの支出・収入のうち支払いの前後60日のもの（`loadReceiptCandidates`）。選ぶとその場で保存し（`linkReceiptToPayment`）、
  上と同じ条件でカテゴリを合わせる。取り込んだ取引のカテゴリを変えたときは `editedFields` に `"lines"` を足し、取り込み元の再同期で戻さない。
  外す（`unlinkReceiptFromPayment`）ときは紐づけだけを外し、入れたカテゴリは戻さない
- 支払いの側からの紐づけは、受け取りの行を `FOR UPDATE` でロックしてから**どこにも紐づいていないことを確かめて**保存する（#1671）。候補を開いたあとに別の画面で
  紐づけられていたら上書きせず、エラーを出して候補を読み直す。同じ支払いへの二重の操作は何もせず成功にする
  - 条件付きの `updateMany` では同時の操作を防げない。`relationMode = "prisma"` の `updateMany` は、条件の `SELECT` と
    id指定の `UPDATE` を別の文で出すため、2つのトランザクションがどちらも条件を満たしたと判断する
- 同時の操作で残っていた競合（#1673）
  - **受け取りの古い編集画面で保存しても、支払い側から付け外しした紐づけを上書きしない。** 編集画面は開いたときの返金元
    （`refundOfEntryIdLoaded`）も送り、画面で返金元を変えていなければ、取引の行をロックしてから読んだいまの値を残す
    （`keepsCurrentRefundLink`・`resolveRefundOfEntryIdOnUpdate`）。送らない経路（振替へのまとめなど）は従来どおり送った値を書く
  - **ロックの順は「取引の行 → 品目」にそろえる。** 取引の編集（`writeEntryUpdateInTx`）・削除（`deleteEntryInTx`）は最初に取引の行を
    `FOR UPDATE` でロックしてから品目を消す。品目を先に消すと、紐づけ（取引 → 品目）と順序が逆になりデッドロックし得る。
    それでもロックの競合（Prisma の `P2034`、生SQLの `P2010` + MySQL 1213/1205）が起きたら、家計簿の操作は生のエラー文ではなく
    「もう一度お試しください」を返す（`lib/db-lock-conflict.ts`）
  - **紐づけは支払いの行も一緒にロックする**（id の昇順）。支払いの削除と同時でも、削除が紐づけを外したあとに書き込んで
    指す先の無い紐づけを残さない（紐づけ側は削除の確定を待ち、「支払いの取引が見つかりません」になる）
  - 候補の検索欄は取引フォームの中にあるので、Enter で取引ごと保存しない

### 立て替え（#880）との使い分け

| | 返金・受け取りの紐づけ（この文書） | 立て替え（`docs/ledger-advances.md`） |
|---|---|---|
| 入れ方 | 支払いはそのまま。受け取ったときにマイナスの支出を入れて紐づける | 支払いの入力で「立て替え」をオンにし、相手と金額を入れる |
| 支出の数え方 | 支払いの日に全額、受け取りの日にマイナス（月をまたぐと月ごとの支出がずれる） | 支払いの日に自分の分だけ |
| 人ごとの残り | 追わない（元の支払いに「実質負担」が出るだけ） | `/ledger/advances` で人ごとに未回収を追う |
