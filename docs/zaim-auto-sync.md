# Zaim 評価額の自動取得

評価額のZaim自動取得（Issue #145）は、**巡回・パースをAIDE（[guchi-apps/aide](https://github.com/guchi-apps/aide)）へ寄せた**（Issue #191）。
Asset Manager はAIDEが日次で巡回した結果を読み取りAPIから受け取り、`Category.valuationAlias` との
対応付けと評価額への反映だけを行う。

## 責務の分担

境界の正はAIDEの `README.md`「asset-manager との境界」にある。

| | 置き場所 |
| --- | --- |
| Zaimの巡回・パース、ログイン状態（storage state）の保持 | **AIDE** |
| 連携口座の更新（ボタン押下）と「最終更新」の取得 | **AIDE** |
| 最終更新が当日でない口座の残高を記録するか | **Asset Manager** |
| `Category.valuationAlias` との照合、評価額への反映 | **Asset Manager**（`lib/zaim-match.ts`・`lib/zaim-sync.ts`） |
| 同期を実行できるユーザーの制限 | **Asset Manager**（`lib/zaim-access.ts`） |

**Asset Manager 側にPlaywrightとZaimのログイン状態は無い。** 以前は「Zaimから取得」を押すたびに
ヘッドレスChromiumを起動して十数秒かかっていたが、いまはAIDEのキャッシュを読むだけになっている。
Zaimのセッション維持（Cookieが2時間で失効する問題）もAIDE側の担当で、このリポジトリには
定期実行もスクリプトも無い。

## 1. AIDEとの接続を設定する

```env
# AIDE側の .env にある AIDE_READ_SECRET と同じ値。未設定なら取得は何もしない。
AIDE_READ_SECRET=
# 接続先。未設定なら http://127.0.0.1:3114（本番VPSでAIDEが待つポート）。
AIDE_BASE_URL=
```

- 本番VPSでは、AIDEも同じサーバー上で動いているため `127.0.0.1` で叩ける。外部公開は不要
- **ローカルでAIDEを起動して確認する場合は `AIDE_BASE_URL` を必ず指定する。** 本番の3114は
  ポート台帳（`guchi-apps/docs` の `standards/ports.md`）で割り当てた値で、AIDEのコード既定は
  4747（`src/server.ts`）。既定値のままローカル起動すると繋がらない
- 実装は `lib/zaim-aide.ts`。`GET /api/money/summary` を1本叩くだけで、Zaimへは取りに行かない
- `AIDE_READ_SECRET` は1Password（`op://apps/aide/read-secret`）が正で、
  `.github/secrets-manifest.tsv` → GitHub Secrets → `deploy.yml` の `env:` → VPSの `.env` の順で配られる。
  値を変えたときは `scripts/sync-github-secrets.sh` でGitHub側へ同期する

### 応答の見方

```jsonc
{
  "empty": false,                       // まだ一度も巡回していなければ true（エラーではない）
  "fetchedAt": "2026-08-25T14:35:00Z",  // AIDEが巡回した時刻
  "ageMinutes": 120,                    // 巡回からの経過分数
  "stale": false,                       // 24時間を超えていれば true
  "balances": [...], "holdings": [...],
  "staleAccounts": [...]                // Zaim側の最終更新が当日でない連携口座
}
```

- **`fetchedAt` と `staleAccounts` の `lastUpdatedAt` は別物。** 前者はAIDEがZaimを巡回した時刻、
  後者はZaimが各金融機関から取得した時刻。Zaimの連携口座は更新に失敗し続けることがあるため、
  巡回が新しくても中身が何日も前ということがある
- AIDEは「古いから返さない」という判断をしない。どう扱うかはAsset Manager側の責務で、
  表示・警告は `lib/zaim-freshness.ts` に畳んである

## 2. Asset Managerとの対応付け

「データ取得状況」画面（`/data-fetch`）の**「Zaim対応付け設定」**にある `valuationAlias` に、Zaim画面上の名称を設定する。同期処理は次の優先順位で対応付ける。

**設定はこの1か所にしかない（#340）。** もとは「評価額一括更新」画面の「表示設定」だったが、
手入力による一括更新が使われなくなったためページごと削除し、未対応の項目が並ぶ「データ取得状況」へ移した。

| 優先 | `valuationAlias` に書く値 | 対象 |
| --- | --- | --- |
| 1 | `口座名/銘柄名#N` | 表示順のN行目を明示的に指定する（通常は不要。下記の自動割り当てを使う） |
| 2 | `口座名/銘柄名` | 同じ銘柄を証券口座ごとに別カテゴリで管理する場合（その口座の同名行の合計） |
| 3 | `銘柄名` | 同じ銘柄を口座をまたいで1カテゴリにまとめる場合（複数口座分を合算する） |
| 4 | 残高一覧の名称 | 銀行・電子マネー等。銘柄を反映していない証券口座の合計もここで扱う |

例えば SBI証券と楽天証券の両方で `eMAXIS Slim 全世界株式` を保有している場合、

- 口座ごとに分けたい → 2つのカテゴリにそれぞれ `SBI証券/eMAXIS Slim 全世界株式`、`楽天証券/eMAXIS Slim 全世界株式` を設定する
- まとめたい → 1つのカテゴリに `eMAXIS Slim 全世界株式` を設定する（両口座の評価額を合算する）

口座名が長いとZaimの画面上で `住信 SBI ネット銀行 投...` のように省略される。省略前の名称は
DOMに存在しないため、`valuationAlias` には省略された表示どおりの文字列を設定する。

### 同一口座内に同名の銘柄が複数行ある場合

同じ証券口座で同じ銘柄を旧NISA・新NISA、つみたて投資枠・成長投資枠などに分けて保有していると、Zaimの証券詳細ページには**同じ銘柄名の行が複数並ぶ**。Zaimはどの行がどの口座区分かを表示せず、行の属性にも情報がないため、**表示順でしか区別できない**。

銘柄名は証券会社由来で利用者が変えられないため、**同じZaim表示名を複数のカテゴリへ設定するだけで、表示順に1行ずつ自動で割り当てる**。`#N` を手で書く必要はない。

```
旧NISA オルカン   → SBI 証券/eMAXIS Slim 全世界株式(オール・カントリー)
新NISA オルカン   → SBI 証券/eMAXIS Slim 全世界株式(オール・カントリー)   ← 同じ値でよい
```

上のカテゴリから順に、証券詳細ページの1行目・2行目が割り当てられる。カテゴリの順番は「Zaim対応付け設定」の並び順（`valuationOrder`）で決まる。逆だった場合はその画面で2つの順番を入れ替える。

- 同じ表示名のカテゴリが**1つだけ**なら、従来どおりその口座の同名行の**合計**になる
- 行数よりカテゴリが多い場合、余ったカテゴリには何も割り当てない
- 割り当てる行が無い名称（銀行口座名など）を複数カテゴリに設定した場合は、先の1件だけに反映する

順番を明示したい場合は `口座名/銘柄名#1` のように `#N` を書ける。手で書いた指定が優先される。`unmatched` も、同名行が複数ある銘柄は `#N` 付きで返す。

**表示順が変わると対応がずれる。** 銘柄の新規購入や全額売却で行が増減した場合は、「Zaim対応付け設定」の「テスト読み込み」で `entries` を確認してから運用を再開する。Zaimが口座区分を表示するようになれば、順番指定に頼らない対応付けへ変更できる。

### 二重計上の防止

同じ資産を複数のカテゴリへ重複して反映しないよう、次のルールで上位に消費された項目を下位の候補から除外する。

- 銘柄を1件でも反映した証券口座は、残高一覧側の口座合計を対応付け対象から外す（`unmatched` にも出さない）
- ある銘柄の一部だけを `口座名/銘柄名` で対応付けた場合、残りの口座分は `銘柄名` だけの alias で合算しない（残りは `unmatched` として報告する）

### 名称の表記ゆれ

ZaimのDOMは名称の途中で要素が分かれて空白・改行が混ざることがあるため、比較時は空白をすべて除去する（`toMatchKey`）。`楽天カー ド` と `楽天カード`、`楽天証券 / eMAXIS Slim 全世界株式` と `楽天証券/eMAXIS Slim 全世界株式` はいずれも一致する。

`valuationAlias` は `,`・`、`・`|` 区切りで複数の名称を設定できる。1つのカテゴリに複数が一致した場合は合算する。

一致しない項目は保存せず、`unmatched` として返す。証券銘柄は `口座名/銘柄名` の表記で返るため、そのまま `valuationAlias` へ貼り付けられる。

### テスト読み込み

対応付けの確認は、「データ取得状況」画面の「Zaim対応付け設定」にある**「テスト読み込み」ボタン**が使える。

- **保存前の編集中のZaim表示名で判定する。** 入力してすぐ結果を確認でき、保存とやり直しを繰り返す必要がない
- 「反映される項目」に、どのカテゴリへどのZaim名称からいくら入るかが出る
- 「未対応のZaim項目」に、どの表示名にも一致しなかった名称が出る。コピーボタンでそのままZaim表示名へ貼り付けられる
- DBへは一切書き込まない

## 3. 画面から取得する

### 利用できるユーザーの制限

AIDEが持つZaimのログイン状態はサーバー上に1つしかないため、誰でも取得ボタンを押せると**他人のZaim残高が自分の資産として反映できてしまう**。これを防ぐため、`ZAIM_SYNC_USER_EMAIL` に設定したメールアドレスのユーザーだけが操作できる。

```env
# 「,」区切りで複数指定できる
ZAIM_SYNC_USER_EMAIL=owner@example.com
```

未設定の場合は誰も使えない。許可されていないユーザーには「今すぐ取り込む」も「Zaim対応付け設定」も表示せず、サーバー側でも実行を拒否する。

ユーザーごとにZaimを連携できるようにするまでの暫定措置。

### 取得の手順

「データ取得状況」画面の**「今すぐ取り込む」**ボタンで取得する。押すとAIDEのキャッシュを読み、
`valuationAlias` と対応付いた値を**その場で評価額へ保存する**（#340）。結果は反映・見送り・未対応の
件数をトーストで返し、明細は同じ画面の実行履歴に `MANUAL` の実行として残る。

**以前はボタンからの取得が「評価額一括更新」画面の入力欄を埋めるだけで、保存は利用者が押していた。**
その画面を削除したため、夜間の定期実行が落ちた日に取り込み直す手段が無くなる。ボタン自体を
保存まで行うものへ変えてある。

定期実行との違いは次の2点で、いずれも**結果を見ている人がいる**ことによる（`runZaimSyncAction`）。

- `overwriteExisting`: その日の値がすでにあっても上書きする（定期実行は当日ぶんに限って上書きする）
- `requireFresh`: 付けない。巡回が古いことは画面の鮮度表示で分かり、古い残高そのものは
  `detectStaleSource` が項目ごとに弾く

±50%を超える異常値を保存しない（`detectLargeDiff`）点は定期実行と同じ。

### いつの値なのかを画面に出す

**AIDEの巡回は日次のため、ボタンを押した瞬間の値ではない。** ボタンの横に
`Zaim取得: 08/25 23:35（2時間前）` のように取得時刻を常時表示し、24時間を超えていれば警告色にする。

- **「今すぐ取り直す」導線は用意していない。** AIDEに再巡回を依頼するAPIが無く、巡回worker自体も
  サブPC側で動いているため。必要になった時点でAIDE側へIssueを立てる
- Zaim側の最終更新が記録日より前の連携口座は、画面からの取り込みでも保存を見送る
  （`detectStaleSource`）。見送った項目は実行履歴の「見送り」に理由付きで残る
- AIDEがまだ一度も巡回していない場合（`empty`）は、エラーではなく「取得結果がまだありません」と出す

## 4. コマンド・APIから取得する

対応付けの初期設定や動作確認には、DBへ書き込まないdry-runを使う。`unmatched` に返る名称を `valuationAlias` へ設定する作業を、一致がなくなるまで繰り返す。

```bash
# VPS・ローカルのコマンドライン（ZAIM_SYNC_SECRET 不要）
npx -y tsx scripts/zaim-sync.ts --dry-run
npx -y tsx scripts/zaim-sync.ts
# 画面のボタンと同じく、当日の評価額があっても必ず上書きする
npx -y tsx scripts/zaim-sync.ts --overwrite
```

`scripts/zaim-sync.ts` は定期実行のエントリでもあるため、`--overwrite` を付けない限り
「記録日が当日のときだけ上書きする」「Zaim側の最終更新が記録日より前の項目は保存しない」
「直近の評価額から±50%を超える値は保存しない」で動く（後述）。`--overwrite` を付けると
前日以前の記録も上書きする。

`ZAIM_SYNC_USER_EMAIL` か `AIDE_READ_SECRET` が未設定の場合は、何もせず正常終了する。
`ZAIM_SYNC_USER_EMAIL` を「,」区切りで複数指定した場合、コマンド・APIからの実行は
**先に書かれたアドレスのユーザー**を同期対象にする（`findZaimSyncUser`）。

HTTP経由でも実行できる。外部から任意のタイミングで叩きたい場合はこちらを使う
（毎日の定期実行はコマンド側で行う。「5. 毎日の定期実行」を参照）。

```env
ZAIM_SYNC_SECRET=<十分に長いランダム文字列>
ZAIM_SYNC_USER_EMAIL=<Asset Managerのユーザーメールアドレス>
```

```bash
curl -X POST -H "Authorization: Bearer $ZAIM_SYNC_SECRET" \
  "https://<asset-manager>/api/zaim/sync?dryRun=1"
```

`entries` に「どのカテゴリへ、Zaim側のどの名称から、いくら反映されるか」が、`unmatched` に「どの alias にも一致しなかった名称」が返る。`dryRun` を外すと実際に保存する。成功時は `updated`、`skipped`、`skippedEntries`、`unmatched`、`entries`、`recordDayKey`、`freshness` をJSONで返す。

`recordDayKey` はAIDEが巡回した日（JST）で、**叩いた日とは限らない**。記録日はAIDEが巡回した
時刻を基準に決まるため（後述）、巡回前に叩けば前日の記録になる。実際の記録日は項目ごとに違い、
`entries[].recordDayKey` に入る（更新の遅い口座は前日ぶんとして書き戻すため。後述）。

## 5. 毎日の定期実行

評価額は毎日 **23:50（JST）** にPM2のcronで自動取得する（`ecosystem.config.js` の
`asset-manager-zaim-sync`）。実体は `scripts/zaim-sync.ts` で、画面のボタンと同じくAIDEのキャッシュを
読んで対応付け、結果をそのままDBへ保存する。

```
npx -y tsx --env-file-if-exists=.env scripts/zaim-sync.ts
```

**AIDE側の巡回より後に動かす必要がある。** AIDEのZaim巡回はサブPCの `aide-zaim-sync.timer` が
23:35 JSTに動かしており、これより先に実行すると前日のキャッシュを読んでしまう。
AIDE側の時刻を変える場合は、こちらの時刻も見直すこと。

### 記録日は「巡回した時刻」から決める（実行時刻ではない）

保存する日付は**AIDEが巡回した時刻（`fetchedAt`）のJST日**で決まる（`lib/zaim-freshness.ts` の
`resolveZaimRecordedAt`）。実行時刻で決めてはいけない。

PM2の `cron_restart` はプロセスを登録するときにも1度起動するため、**デプロイのたびに
`scripts/zaim-sync.ts` が日中に1回走る**。そのとき読めるのは前夜23:35の巡回結果で、中身は
前日の残高そのものになる。実行時刻で日付を決めていると、この値が当日の評価額として静かに
記録され、さらにその晩23:50の本実行は「当日の評価額がすでにある」で通知もされずスキップされる。
**結果として、当日の評価額が前日の値と一致したまま固定される**（#254）。

記録日を巡回時刻から決めることで、デプロイ直後の実行は前日ぶんの記録として扱われ、当日の値を
作らない。ログの `巡回日:` 行に、その実行が読んだ巡回結果の日付が出る。

### 巡回時刻に間に合わない口座は、その値が属する日へ書き戻す

巡回日は**全項目の記録日ではない**。実際の記録日は項目ごとに決まる（`resolveEntryRecordDayKey`）。

`aide-zaim-refresh` は23:15に連携口座の更新を押して5分待つが、**SBI証券は毎晩23:50頃にしか
反映されない**（楽天証券・Ponta・MUFGカードも同様）。23:35の巡回では、これらの口座は
いつも前日の残高のままになる。実際、2026-08-26 23:35の巡回結果ではSBI証券の
`lastUpdatedAt` が `2026-08-25T23:50:43+09:00` だった（#258）。

- 当日の値として保存すると、前日の残高が当日の評価額になる（#254 と同じ状態）
- 鮮度で弾くと、SBI証券の約287万円が**毎晩1件も記録されず**評価額が固定される

どちらでもなく、**その行の最終更新日（JST）を記録日にする**。上の例ならSBI証券由来の項目は
`2026-08-25` ぶんとして保存され、翌晩の実行で前日の値が正しく埋まる。

- 書き戻すのは**巡回日の前日まで**（`ZAIM_BACKFILL_MAX_DAYS`）。連携設定が壊れた口座は
  何日・何ヶ月も最終更新が進まないため、遠い過去を古い値で塗り替えないようにする。
  それより古い項目は従来どおり `staleSource` で保存を見送る
- 最終更新を持たない口座（現金・手入力）と、最終更新が巡回日以降の口座は巡回日へ記録する
- 書き戻しは、その日にすでに評価額があっても**上書きする**（`canOverwriteRecordDay`）。
  Zaimがその日の確定値を持っているのに対し、入っている値は前日から持ち越した古い値のため
- **当日の合計は、更新の遅い口座のぶんだけ前日の値を持ち越したままになる**（履歴グラフは
  `lib/history-compute.ts` が直近の評価額を持ち越すため欠けない）。翌晩の実行でその日の値が
  確定する。当日のうちに揃えるにはAIDE側で `aide-zaim-refresh` を前倒しする必要がある

PM2のプロセスはVPS上の `.env` を自動で読み込まないため、Nodeの `--env-file-if-exists` を
tsx経由で渡している（`AIDE_READ_SECRET` は `.env` にしか無い）。tsxは未知のフラグをそのままNodeへ渡す。

**cronの発火時刻はサーバーのタイムゾーンで決まる。** PM2の `cron_restart` はPM2デーモン側で
評価されるため、`env_production` に `TZ` を書いても発火時刻は変わらない。本番VPSは
`timedatectl set-timezone Asia/Tokyo` を実施済みで（`guchi-apps/vps` の `docs/initial-setup.md`）、
JSTで発火する前提。サーバーのタイムゾーンを変える場合は、記録日（JST固定）とずれるため
この時刻も見直すこと。

### 確認する人がいないぶんの安全策

画面のボタンは「取得 → 合計・前回差分を目視 → 保存」の2段階だが、定期実行にはその確認が無い。
`valuationAlias` の対応付けミスや、同一口座内に同名銘柄が複数ある場合の表示順ずれが、
そのままDBへ入るのを防ぐため、定期実行では次の3つを必ず通す
（前2つの判定は `lib/zaim-sync-policy.ts`、鮮度の判定は `lib/zaim-sync.ts`）。

| 状況 | 挙動 |
| --- | --- |
| 記録日が当日で、すでに評価額がある | **上書きする**。誤った値が入っても、その晩の実行で正しい値へ直る |
| 記録日が前日以前で、すでに評価額がある | 上書きせずスキップする（デプロイ直後の1回実行がここに当たる） |
| Zaim側の最終更新が巡回日の前日 | **前日ぶんとして保存する**（書き戻し。前述） |
| Zaim側の最終更新が2日以上前 | 保存せずスキップする（`detectStaleSource`）。通知は1件も保存できなかった日だけ |
| 直近の評価額から±50%を超えて動いた | 保存せずスキップして通知する（閾値は `lib/valuation-diff.ts` の `LARGE_VALUATION_DIFF_RATIO`） |
| AIDEの巡回結果が古い（24時間超）・まだ無い | **1件も保存せず、通知して異常終了する**（`requireFresh`） |

**当日ぶんは上書きする。** そのため、その日に画面から手で直した評価額は、同じ日の夜のZaim取得で
上書きされる。前日以前の記録は上書きしない。

**Zaim側の最終更新が記録日より前なら保存しない。** 連携口座は更新ボタンを押しても金融機関側の
都合で当日にならないことがあり（AIDEの `aide-zaim-refresh` は5分待って諦める。2026-08-24は29口座が
当日にならなかった）、その残高を記録日の評価額として保存すると前日の値がそのまま入る。前日比の
差は小さいため±50%の検知にも掛からない。判定は行ごとの `lastUpdatedAt` で行う（`lib/zaim-freshness.ts`
の `isStaleForDay`）。**連携していない口座（現金・手入力）は最終更新を持たない（`null`）ため対象外**で、
従来どおり保存する。1件でも古い行を合算したまとまりは、合計そのものが古いとみなしてスキップする。

記録日は最終更新の日から決まるため（前述）、この判定に掛かるのは**書き戻せる範囲より古い
＝連携が止まっている口座**だけになる。

**スキップしても履歴のグラフは欠けない。** `lib/history-compute.ts` はカテゴリごとに直近の評価額を
持ち越すため、その日の記録が無いカテゴリは前回の値のまま描かれる。古い残高を当日の値として
書き足すより、記録しないほうが履歴としては正確。

**個別の通知は出さない。** 連携設定が壊れた口座は何日・何ヶ月も最終更新が進まないため
（AIDEの `parse.ts` の `findStaleZaimAccounts` のコメントを参照）、項目ごとに通知すると毎日同じ
内容が飛ぶ。**その日1件も保存できなかったときだけ**まとめて通知する。恒常的に更新が通らない
口座がある場合、直すのはZaim側の連携設定であってこちらの判定ではない。

**巡回が止まっていてもAIDEは200を返す。** 中身は前回巡回時の残高のままなので、そのまま保存すると
前日の値が当日の評価額として静かに記録される。しかも前日比の差は小さいため±50%の検知にも掛からない。
サブPCが止まっていた日にこれが起きるため、定期実行は保存の前に鮮度で止める（`lib/zaim-sync.ts` の
`requireFresh`）。画面のボタンは目視で確認できるので、古くても取得して警告を出すだけにしている。

- 比較の基準は「記録日分があればその値、無ければそれ以前の直近の評価額」。初回の記録で基準が無い場合は比較せず保存する
- 前日以前の記録も含めて意図的に上書きしたい場合は `--overwrite` を付ける
- `/api/zaim/sync` は従来どおり無条件に上書きし、異常値・最終更新の検知も行わない（呼び出し側が結果を確認できるため）。ただし**記録日の決め方は同じ**で、応答の `recordDayKey` で確認できる
- そのため `/api/zaim/sync` にも `requireFresh` を入れている。記録日が巡回時刻で決まる以上、巡回が何日も止まった状態で叩くと**過去日の記録を上書きしてしまう**ため。見送った場合は応答の `staleSkipped` が `true` になる

### 失敗・スキップの通知

`SIGNALY_ZAIM_SYNC_WEBHOOK_URL` を設定すると、次の場合にSignalyへ通知する。未設定なら通知を
スキップして正常終了するため、設定していない環境でも失敗しない。

- 取得・保存が例外で失敗した
- 異常値・鮮度・保存失敗で保存を見送った項目があった
- **AIDEの巡回結果が古い（24時間超）か、まだ一度も無い。** この場合は保存を見送って終了する
  （後述）

「記録日の評価額がすでにある」ためのスキップは想定内の動作なので、ログにだけ出して通知しない。
デプロイのたびに走る1回実行はほぼ必ずこれに当たるため、通知の対象にすると毎回鳴ってしまう。

値は他のSignaly通知と同じ配布経路に載せている。1Password（人が管理する唯一の正）→
`.github/secrets-manifest.tsv` → GitHub Secrets → `deploy.yml` の `env:` → VPSの `.env` の順に配られる。
1Passwordの項目は `op://apps/AssetManager/zaim-sync-webhook-url`。値を変えたときは
`scripts/sync-github-secrets.sh` でGitHub側へ同期する。

### 実行結果を画面から追う（`/data-fetch`）

通知は**異常時にしか飛ばない**ため、うまくいった日に何が反映されたのかは残らなかった。
Issue #269 で、実行のたびに結果を `DataFetchRun` / `DataFetchItem` へ記録し、
サイドバーの「データ取得状況」（`/data-fetch`）から日ごとに確認できるようにしている。

- 記録するのは `scripts/zaim-sync.ts`（Zaim評価額）と `scripts/fetch-index-values.ts`（指数）。
  どちらも `recordDataFetchRun`（`lib/data-fetch-log.ts`）を呼ぶ
- **記録は表示のためだけのもので、取得・保存の成否を左右しない。** `recordDataFetchRun` は
  例外を投げず、失敗してもログに出すだけで呼び出し元を止めない（ログの書き込み失敗で
  毎晩の定期実行を落とさないため）
- 明細は「反映（`REFLECTED`）／見送り（`SKIPPED`）／未対応（`UNMATCHED`）／失敗（`FAILED`）」の
  4種類。見送りの理由コードは `ZaimSkipReason` をそのまま入れており、画面の文言は
  `describeDataFetchReason`（`lib/data-fetch-view.ts`）が持つ
- 「1件も反映できなかった」と「取得元が古くて保存に進まなかった」は原因が違うため、
  後者は `nothingSaved` を立てて実行の状態を `SKIPPED` にする
- 記録は90日で打ち切る（`DATA_FETCH_RUN_RETENTION_DAYS`）。`relationMode = "prisma"` で
  外部キーが無いため、明細を消してから実行を消す
- 画面には取得元（AIDE）の残高・保有銘柄そのものも並べている。「Zaimには載っているのに
  反映されていない」を1画面で追えるようにするため
- **デプロイ直後の1回は `trigger` で区別する**（#276）。下の「デプロイ直後の1回」のとおり
  `cron_restart` は登録時にもプロセスを起動するため、日中のデプロイでも前夜のキャッシュを読む
  実行が1回入る。これを最新の実行として出すと「今日は1件も反映されていない」と読めてしまうので、
  最新カードが拾うのは `SCHEDULED` の実行だけにしている。判定は起動時のJST時刻が
  cronの発火時刻から30分以内か（`resolveDataFetchTrigger`）で、PM2の外で動かしたぶんは `MANUAL`

### デプロイ直後の1回

PM2の `cron_restart` は登録時にもプロセスを1度起動するため、デプロイ直後に1回実行される。
このとき読むのは前夜23:35の巡回結果なので、**記録日は前日**になる（前述）。前日の評価額は
すでに前夜の本実行が入れているため、上書きせずスキップして終わる。

`.github/workflows/deploy.yml` が `pm2 start ecosystem.config.js` を毎回叩くため、この1回実行は
デプロイのたびに起きる。「日中に走っても当日の記録を汚さない」ことが前提になっているので、
記録日の決め方（`resolveZaimRecordedAt`）を変えるときはここも一緒に見直すこと。

## 評価額がZaimの表示と合わないときの調べ方

**まず「利用者が見ている金額が何の合計か」を特定する。** Zaimの残高画面は口座を種別
（銀行・クレジットカード・電子マネー・ポイント・投資）でまとめて小計を出すため、挙がった
金額が総資産とは限らない。AIDEのスナップショット（`GET /api/money/summary` の `balances`）に
対して部分和を探すと一意に決まることが多い。#258 では `4,502,155` が
`SBI 証券 + ハイブリッド預金 SBI証券 + 確定拠出年金（NRK） + bitFlyer` の「投資」小計だと分かり、
そこから追う範囲が絞れた（本番DBへ接続せずに原因まで辿れる）。

次に見るのは**行ごとの `lastUpdatedAt`**で、`fetchedAt`（AIDEが巡回した時刻）ではない。
巡回が当日でも中身が前日ということがあり、それが差の正体であることが多い。
サブPCで `journalctl --user -u aide-zaim-refresh.service` を見ると、その晩に何口座が
当日更新にならなかったかが残っている。

## セキュリティ

- `AIDE_READ_SECRET` はパスワード相当の秘密情報として扱う。Gitへコミットしない
- AIDEの読み取りAPIはVPS内の `127.0.0.1` からのみ叩く。公開URL側は
  `guchi-apps/vps` のApache設定で `/api/money`・`/api/zaim` を遮断している
- 同期エンドポイント（`POST /api/zaim/sync`）は `ZAIM_SYNC_SECRET` のBearer認証を必須とする
- Zaimのログイン状態（storage state）はこのリポジトリでは扱わない。AIDE側の
  `data/zaim/storage-state.json` に一本化した
